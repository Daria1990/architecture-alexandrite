# Выбор и настройка мониторинга в системе

## Мотивация

**Сейчас команда узнаёт о проблемах от клиентов.** Алертов нет, поэтому команда не видит, что происходит в системе. Например, если на сервере заканчивается память, это можно заметить заранее и исправить. Но сейчас команда узнает о проблеме, только когда система упадёт и клиенты начнут жаловаться.

**Это уже стоит компании денег.** «Александрит» потерял несколько крупных контрактов из-за проблем с заказами. API-клиенты каждый день сообщают, что не получили заказы, недовольство B2C-клиентов растёт. Команда узнаёт об этом последней и не может быстро найти, где и почему теряется заказ.

**Яндекс Метрика больше не даёт полной картины.** Она видит только то, что происходит на сайте. Заказы через API идут мимо сайта, поэтому самый проблемный поток заказов сейчас вообще не виден. Состояние серверов, баз данных и очередей Метрика тоже не показывает.

**Что даст мониторинг:**
* **Замечать проблему раньше клиента.** Алерт приходит, когда проблема только начинается, а не когда клиенты уже пострадали.
* **Быстро находить, где проблема.** Видно, в какой системе растут ошибки, где копятся сообщения в очереди и что начало тормозить.
* **Проверять, помогают ли улучшения.** Появляется точка отсчёта: по цифрам видно, стало ли лучше после изменений из Task1.
* **Готовиться к росту нагрузки.** Заказов становится больше на 100 каждый месяц. Мониторинг покажет, когда система подойдёт к пределу, заранее, а не в момент отказа.

## Выбор подхода к мониторингу

RED — для сервисов, которые отвечают на запросы. USE — для ресурсов. Четыре золотых сигнала — там, где важно и то и другое.

| Часть системы | Подход | Почему |
|---|---|---|
| Shop API | RED | Отвечает на запросы покупателей. Важно, сколько запросов, сколько из них с ошибкой и как быстро идёт ответ. |
| MES API (включая запросы партнёров) | Четыре золотых сигнала | Кроме запросов, считает цену 2–30 минут и грузит CPU единственного инстанса. Важно видеть, насколько он близок к пределу. |
| CRM API | Четыре золотых сигнала | Кроме запросов продавцов, разбирает сообщения из RabbitMQ. Если не успевает, сообщения копятся, а это и есть насыщенность. |
| RabbitMQ | USE | Ресурс: важно, сколько сообщений в очереди и успевают ли их разбирать. |
| Shop DB, MES DB | USE | Ресурс: важно, хватает ли памяти, соединений и места. |
| S3-хранилище | USE | Ресурс: важно, сколько места занято. |

Фронтенды (Vue, React) в таблицу не входят: они работают в браузере пользователя, а поведение на сайте видит Яндекс Метрика.

## Метрики

### Shop API (RED)

| Метрика | Зачем | Ярлыки |
|---|---|---|
| 3. Number of requests (RPS) for internet shop API | Видеть нагрузку и её рост | `endpoint` — какой запрос |
| 28. Number of `HTTP 500` for shop API | Видеть, что у покупателей что-то сломалось | `endpoint` — какой запрос падает |
| *своя:* процент ошибок | Понять, много ли ошибок относительно нагрузки | Не нужны: считается из запросов и ошибок |
| 19. Response time (latency) for shop API, p50/p95/p99 | Медленный сайт — клиент уходит | `endpoint` |

### MES API (четыре золотых сигнала)

| Метрика | Зачем | Ярлыки |
|---|---|---|
| 5. Number of requests (RPS) for MES API | Видеть нагрузку от операторов и партнёров | `endpoint`; `client` — оператор или партнёр; `partner` — какой партнёр |
| 30. Number of `HTTP 500` for MES API | Видеть, что заказы партнёров или работа операторов падают | `endpoint`, `client`, `partner` |
| *своя:* процент ошибок | Понять, много ли ошибок относительно нагрузки | Не нужны: считается из запросов и ошибок |
| 21. Response time (latency) for MES API, p50/p95/p99 | Видеть, что тормозит; расчёт цены виден отдельно по `endpoint` | `endpoint`, `client` |
| 11. CPU % for MES API | Расчёт цены грузит CPU, видно, когда MES у предела | Пока не нужны, инстанс один. Потом `instance` |
| 14. Memory Utilisation for MES API | Заметить нехватку памяти до падения | Пока не нужны. Потом `instance` |
| *своя:* сколько расчётов цены ждут и сколько идут | Видеть, что MES не успевает считать | `state` — ждёт или считается |

### Inbox / outbox (после внедрения)

| Метрика | Зачем | Ярлыки |
|---|---|---|
| *своя:* сколько записей пришло и сколько обработано в секунду | Видеть, что обработка успевает за потоком | `system` — MES, CRM или магазин; `type` — inbox или outbox |
| *своя:* сколько записей не обработано | Видеть, что записи копятся | `system`, `type` |
| *своя:* график попыток обработки: сколько упало | Видеть, что заказы не проходят обработку | `system`, `type` |

## План действий

1. **Хранилище метрик** — развернуть Prometheus. Это time-series БД, куда стекаются все метрики.
2. **Метрики серверов** (CPU, RAM) — поставить на виртуальные машины node_exporter.
3. **Метрики БД** — подключить postgres_exporter к Shop DB и MES DB.
4. **Метрики RabbitMQ** — включить встроенный плагин `rabbitmq_prometheus`.
5. **Метрики S3** — забирать объём хранилища из Yandex Monitoring.
6. **Метрики в Shop API и CRM API** (Spring Boot) — подключить Micrometer, добавить ярлыки `endpoint`.
7. **Метрики в MES API** (C#) — подключить библиотеку prometheus-net, добавить ярлыки `endpoint`, `client`, `partner` и свою метрику очереди расчётов цены.
8. **Дашборды** — развернуть Grafana, сделать по дашборду на каждую часть системы.
9. **Алерты** — настроить Alertmanager: пороги и куда слать (Telegram, звонок).
10. **Inbox / outbox** — после внедрения добавить их метрики.

## Пороги насыщенности

Порог считается превышенным, если значение держится несколько минут. Так короткий всплеск не будит людей.

| Показатель | Warning (Telegram) | Alarm (звонок) | Почему такой порог |
|---|---|---|---|
| CPU API (10, 11) | > 70% 10 минут | > 90% 5 минут | При 70% ещё есть запас на всплеск. При 90% запросы начинают ждать процессор, ответы тормозят. |
| RAM API и БД (13–16) | > 80% | > 90% | При нехватке памяти система убивает процесс, и сервис падает целиком. |
| Соединения БД (17, 18) | > 70% от максимума | > 90% от максимума | При 100% новые запросы получают ошибку. |
| Размер БД (23, 24) | > 75% диска | > 90% диска | При полном диске БД перестаёт принимать запись, то есть новые заказы. |
| Сообщения в очереди RabbitMQ | Растёт 10 минут подряд | Растёт 30 минут подряд | Если очередь растёт, получатель не успевает, и заказы копятся. |
| DLQ (1) | Любое новое сообщение | > 10 сообщений за 10 минут | Каждое сообщение в DLQ — необработанный заказ. Много сразу — сломалось что-то глобальное. |
| Очередь расчётов цены в MES | Растёт 30 минут подряд | Растёт 1 час подряд | Расчёт идёт до 30 минут. Если очередь растёт дольше, MES не справляется. |
| Процент ошибок API | > 1% 5 минут | > 5% 5 минут | Не насыщенность, но резкий рост ошибок — глобальная проблема, поэтому тоже звоним. |

## Что происходит при превышении

- **Warning** — сообщение в Telegram-канал команды. Дежурный смотрит в рабочее время.
- **Alarm** — звонок, только на глобальные проблемы: резкий рост ошибок, много застрявших сообщений.
- **Эскалация звонка.** Сначала звонок дежурному. Если он не ответил за 2 минуты, звонок ему повторяется. Если снова нет ответа за 2 минуты, звонок уходит запасному дежурному, потом тимлиду, потом начальнику отдела, по той же схеме.
- **Система дежурств.** Дежурный и запасной дежурный меняются по графику.
- **Инциденты** заводятся автоматически на каждый alarm. Дежурный заполняет инцидент и анализирует причину.
- **Разбор раз в 2 недели.** Команда обсуждает инциденты и решает, что сделать, чтобы они не повторились. Эти задачи уходят в разработку.
